❯ What's ALFRED?

● ALFRED stands for ArchivaL Federal Reserve Economic Data. It's the St. Louis
  Fed's companion to FRED.

  - FRED shows each series as it stands today, with all revisions applied. Ask
    FRED for September 2026 ADP employment and you get the current, revised
    value.
  - ALFRED shows each series as it stood on any past date. Every time a release
    revises the data, ALFRED keeps the old version, called a vintage. You can
    ask it "what did this series look like on 2026-10-01?" and get exactly what
    the market saw that morning.

  Why it matters here:

  1. First print vs. revised. ADP revises the prior month with each release.
     ALFRED lets you recover the first-reported number for every month, which is
     what traders reacted to and what your forecast is really trying to
     predict.
  2. An honest backtest. To test "what would my model have predicted for
     October?", the model may only see data as it existed before October's
     release. If you backtest on today's revised FRED data, the model uses
     information that didn't exist yet (look-ahead bias). That makes your
     accuracy numbers look better than they really are. ALFRED vintages remove
     that problem.
  3. Same API. ALFRED uses the same FRED API and the same free key. You add
     realtime_start / realtime_end parameters (or vintage_dates) to the
     observations call. That makes it a small detail of the source adapter, not
     a separate integration.

  The interview line: "I backtest against point-in-time vintages, so the model
  never sees revisions that hadn't been published yet." Reviewers at a
  markets-oriented firm will notice that sentence.

  Question 5: How does forecasting work, and how does it explain itself?

  This is the core of the submission, because "understand why you predicted what
  you did" is a hard requirement.

  My recommendation is the Strategy pattern, with explainability built into the
  return type:

  interface Forecaster {
      String name();
      Forecast forecast(PrintHistory asOf);   // point-in-time history only
  }

  record Forecast(ReferenceMonth target, JobsChange point,
                  Interval range, Explanation why) {}

  Each model has to explain its own number, because only the model knows why it
  chose it. Rendering that explanation to the terminal is a separate class
  (single responsibility).

  Models to ship. Few, simple, and each easy to explain:

  1. NaiveForecaster: next = last print. This is the baseline every other model
     must beat. Without it, your accuracy numbers mean nothing.
  2. MovingAverageForecaster(k): mean of the last k prints. Explanation:
     "average of Jul/Aug/Sep = …".
  3. AutoregressiveForecaster(p): AR(p) fit by ordinary least squares (Apache
     Commons Math). Its explanation is the strongest: the forecast decomposes
     into intercept + Σ coefficient × lag, so you can print each lag's
     contribution in thousands of jobs.
  4. EnsembleForecaster (Composite pattern): weights each child model by its
     inverse backtest error. Explanation: "60% AR(3), 30% MA(3), 10% naive,
     because those were their recent error rates." It's the best illustration of
     composition, which they explicitly grade.

  Deliberately cut: ARIMA with seasonality (the series is already seasonally
  adjusted), machine-learning models, and exogenous predictors (deferred to
  "next week," but the PrintHistory input can later grow into a feature set).

  Do you agree with these four models, with the ensemble as the default forecast
  output? Or do you want to stop at three and skip the ensemble to keep scope
  tight? I'd keep it: it's about 50 lines and it's the strongest composition
  story in the walkthrough.

  Question 6: How do you measure forecast accuracy?

  The brief says to "pick an approach, justify it, and show your work."

  My recommendation is a walk-forward backtest against first prints:

  for each month M in the test window:
      history  = everything as it was published BEFORE M's release
  (point-in-time vintage)
      forecast = model.forecast(history)
      actual   = M's FIRST print
      record error = forecast − actual

  Justification you'll defend:

  - Walk-forward, not a single train/test split. It mirrors how the tool is
    actually used, re-forecasting every month with whatever data exists at that
    point.
  - Score against the first print. That's the number the market sees and reacts
    to on release day, so it's the number worth predicting.
  - Point-in-time history. This prevents look-ahead bias (see the ALFRED
    explanation). It's also why we modeled revisions in Q2. Each decision so far
    supports the next one, which is a good thread to point out in the
    walkthrough.

  Metrics. Two, both easy to explain:

  - Mean absolute error (MAE), in thousands of jobs. A non-technical reader
    understands "off by 38K on average."
  - Skill vs. naive = 1 − MAE_model / MAE_naive. A positive value means the
    model beats the baseline; zero or negative means it's worthless. This one
    number answers "is the model any good?"

  Design: a Backtester takes a Forecaster and returns a BacktestReport. An
  AccuracyMetric interface keeps metrics pluggable, though you'll ship only
  these two. Exposed as adp backtest --model ar --from 2015-01.

  Do you agree with walk-forward against first prints, scored by MAE and skill
  vs. naive? The next question is about the test window, specifically the 2020
  COVID months. ADP printed swings in the millions that year, and they will
  dominate both the model fit and the error numbers if left in.

  1. Exclude a fixed window (Mar 2020 – Dec 2021) from both fitting and scoring.

  3. Keep everything and use robust methods (median absolute error, robust
     regression). More sophisticated, and harder to explain.

  Fit-window effects (AR model only; the naive model ignores the window, since
  it uses only the last print):

  - Including COVID: least squares chases the multi-million swings. The
    coefficients end up describing extreme crash-and-rebound behavior, and
    normal-month forecasts get distorted.
  - Long window (e.g. 2010–now): more data, so more stable coefficients. But it
    mixes in older regimes (for example, the 2010s pattern of steady
    ~+200K/month), which pulls the forecast toward an outdated average.
  - Short window (e.g. last 36 months): adapts to the current regime, but fewer
    data points mean noisier coefficients that can swing between runs.

  That's the classic bias–variance trade-off, and naming it in the README is a
  strong signal.
